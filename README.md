## Домашнее задание к занятию «Базы данных, их типы»

### Задание 1. СУБД
<details>
  <summary>Текст задания</summary>

Кейс
Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для каждой предметной области.

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему?

1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.

1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.

1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.

1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать со связями.

</details>


**1.1.** Для бюджетирования выбрал бы реляционную СУБД, например PostgreSQL. Бюджеты, расходы и платежи удобно хранить в связанных таблицах. Транзакции и ограничения помогут сохранить целостность данных, а SQL подойдёт для финансовых отчётов. Прогнозирование рисков можно делать отдельным инструментом на основе этих данных.

**1.2.** Для лендингов подойдёт документная СУБД, например MongoDB. У проектов могут быть разные формы заявок, поэтому удобно хранить данные без одинакового набора полей для всех лендингов.

Для CRM выбрал бы PostgreSQL: клиенты, сделки и менеджеры связаны между собой, нужна целостность данных. Дополнительные поля можно хранить в JSONB. Скорость в обоих случаях зависит также от индексов и запросов.

**1.3.** Подойдёт иерархическая модель: компания → отдел → подразделение → материалы. Сотрудникам будет понятно, где искать нужные нормы и инструкции. Такая структура удобна, если у каждого раздела один родитель.

**1.4.** Для логистики выбрал бы графовую СУБД, например Neo4j. Объекты и точки доставки можно представить вершинами, дороги — связями с расстоянием и временем в пути. Это удобно для поиска маршрутов. Распределение курьеров с учётом загрузки и сроков уже выполняется алгоритмом на основе данных из базы.

### Задание 2. Транзакции

<details>
  <summary>Текст задания</summary>

2.1. Пользователь пополняет баланс счёта телефона, распишите пошагово, какие действия должны произойти для того, чтобы транзакция завершилась успешно. Ориентируйтесь на шесть действий.

</details>

**2.1.** Пополнение баланса телефона:

1. Пользователь вводит номер телефона, сумму и выбирает счёт для оплаты.
2. Система проверяет номер, сумму и наличие денег, создаёт платёж с уникальным идентификатором.
3. Банк списывает деньги и фиксирует платёж в своей транзакции.
4. Платёжная система передаёт оператору номер, сумму и идентификатор платежа.
5. Оператор зачисляет деньги на баланс и подтверждает результат. Повторный запрос с тем же идентификатором не должен приводить к повторному зачислению.
6. Система отмечает платёж как успешный и отправляет пользователю подтверждение.

У банка и оператора отдельные транзакции. Если подтверждение не пришло, нужно проверить статус платежа и повторить запрос. Если зачисление невозможно, оформить возврат.

### Задание 3. SQL vs NoSQL

<details>
  <summary>Текст задания</summary>

3.1. Напишите пять преимуществ SQL-систем по отношению к NoSQL.

</details>

**3.1.** Пять преимуществ SQL-систем:

1. Чёткая схема данных: типы и обязательные поля проверяются самой СУБД.
2. Внешние ключи и ограничения помогают сохранить целостность связанных данных.
3. Транзакции позволяют выполнить несколько изменений целиком или отменить их.
4. JOIN позволяет объединять данные из нескольких таблиц одним запросом.
5. SQL удобен для сложных отчётов: группировок, агрегатов и оконных функций.

У отдельных NoSQL-систем часть этих возможностей тоже есть, но для реляционных СУБД это стандартный набор.

### Задание 4. Кластеры

<details>
  <summary>Текст задания</summary>

Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу выделено 1000 машин.

На основе какого критерия будете выбирать тип СУБД и какая модель распределённых вычислений здесь справится лучше всего и почему?

</details>

Выбирал бы по характеру нагрузки: нужны массовые вычисления над всем набором данных или быстрые запросы к отдельным записям. Также важны возможность распределить данные между узлами и работа при отказе части машин:

Для массовой пакетной обработки на 1000 машинах подойдёт распределённая аналитическая СУБД или хранилище, а модель вычислений — MapReduce. На этапе Map машины параллельно обрабатывают свои части данных, затем результаты группируются по ключу и объединяются на этапе Reduce.

Так можно распределить большой объём работы и повторно запустить задачи с отказавших узлов. Вычисления лучше выполнять ближе к данным, чтобы меньше передавать по сети. Для частых повторных расчётов имеет смысл использовать Spark: он может держать промежуточные данные в памяти.
